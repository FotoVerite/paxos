Why Vertical

The authors are using horizontal as shorthand for the old way of doing reconfiguration in Paxos. The idea is that configuration changes happen as you move across the sequence of instances, not as you move down through ballots inside one instance. That means you have to reason about configuration changes in the same place you are already reasoning about the log, leadership and application to state.

The annoying part is quorum intersection. If the acceptor set changes across configurations, you still need the new setup to overlap with the old one in the right way, or safety falls apart. In the older framing, that coupling lives across the horizontal progression of the protocol. Or was removed by fully stopping and starting a new instance with a checkpoint. Vertical Paxos moves that coupling into the ballot/leadership entirely.

With Vertical Paxos this is no longer the case. Each ballot is tied to one configuration and one set of acceptors. That is the whole trick. You are no longer pretending one fixed acceptor set owns the whole story while the system changes around it. The relevant acceptor set is attached to the ballot/configuration you are in.

So the name is not about “vertical integration” or any other grand idea. It is literally Lamport naming the thing after the direction in his array picture. Slightly silly, yes, but at least this time the silly name points at a real structural change.
