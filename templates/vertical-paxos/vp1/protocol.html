VP I - Protocol

VP I still looks like Paxos on the surface: phase 1 asks what older ballots still matter, and phase 2 pushes one value through. The difference is that leadership and configuration are assigned externally by the ACM, and the recovery step cannot assume one fixed acceptor set stretching forever into the past. That is why FindSafe has to become VFindSafe

Steps
1a

1a

Request each acceptor a to set maxBallot[a] to m.bal and report the value of vote[a][m.prevBal].

Acceptor a ignores the message if m.bal < maxBallot[a].

The leader starts by asking acceptors to move up to this ballot and report what they already know about the earlier one. The message will be ignored if acceptors have seen a ballot greater than this ballot.

1b

1b

Assert that maxBallot[m.acc] ≥ m.bal and vote[m.acc][m.voteBal] = m.val.

The notation here is doing something annoying. It writes the reply in terms of the acceptor's state variables, which makes it sound like the message and the state are the same thing. They are not. 1b is just the acceptor reporting back what it currently knows about the earlier ballot the leader asked about.

2a

2a

Request each acceptor a to set vote[a][m.bal] to m.val.

Acceptor a ignores the message if m.bal < maxBallot[a].

This is the point where the leader stops asking questions and starts trying to make one value stick. That value is either the safe value recovered from phase 1 or, if phase 1 came back `AllSafe`, a fresh client value. If acceptors have already moved on, they ignore it.

2b

2b

Report that acceptor m.acc has voted for m.val in ballot m.bal.

2b is the acceptor saying it voted for this value in this ballot. That is how the leader learns phase 2 actually took. If too many acceptors have already moved on, those replies stop materializing, which is also its own answer.
