Replicas and Slots

Before we talk about consensus, we need to understand the structure that makes ordering work. That structure is built on two simple ideas: replicas and slots.

What is a replica?

A replica is a state machine. It maintains application state. When a client sends a request, the replica receives it, executes the command, and returns a result.

In single-server systems, you'd have one replica. In Paxos, you have many replicas. They all maintain identical state and execute commands in the same order. From the client's perspective, they look like a single, fault-tolerant server.

The slot abstraction

Here's the key insight: instead of replicas directly executing commands as they arrive (which would cause ordering problems), they execute commands from a sequence called a log.

Each position in the log is a slot. Slot 1, slot 2, slot 3. Each slot will eventually hold a command. Replicas execute slot 1, then slot 2, then slot 3, and so on.

The question is: which command goes in which slot? When multiple clients send requests concurrently, they might propose different commands for the same slot. The Synod protocol (which we'll see next) decides that.

How replicas handle requests

When a replica receives a client request for command c, it does something simple: find the lowest slot that hasn't been filled yet, and propose command c for that slot.

Then the replica waits. It doesn't execute the command yet. It waits for a decision from the consensus mechanism (Synod). Once a decision arrives, the replica knows which command actually won the slot. It executes the command and sends a response to the client.

This is the core of state machine replication: all replicas see the same sequence of decisions, so they all execute the same sequence of commands in the same order, resulting in identical state.

Multiple clients, same slot

Here's where it gets interesting. Suppose two clients send requests to different replicas at the same time. Replica A receives a request for command c1. Replica B receives a request for command c2. Both propose their commands for slot 1.

Now we have a conflict: which command should actually be in slot 1? The Synod protocol handles this. It ensures that one of them wins (only one value is chosen), and all replicas agree on the winner.

If replica A's command loses, it doesn't disappear. Replica A re-proposes it for a higher slot number. Eventually, all client commands get into the log, just in some order determined by Synod.
