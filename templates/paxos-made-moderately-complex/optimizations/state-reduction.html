State Reduction

NVM $\alpha.accepted$ simplified

First note that although a leader obtains a set of all accepted pvalues from a majority of acceptors, it only needs to know, for each slot, whether this set is empty or not, and if not, what the maximum pvalue is. Thus, a large step toward practicality is that acceptors only maintain the most recently accepted pvalue for each slot (⊥ if no pvalue has been accepted) and return only these pvalues in a p1b message to the scout. This gives the leader all information needed to enforce Invariant C2.

RENESSE, P. 12 §4.1 - Paxos Made Pragmatic

For $\alpha.accepted$, we are only concerned about the maximum tuple of (b, s, c). Any other tuple with a smaller b for a slot s can be discarded. This alone is all the leader needs to enforce C2, Command Consistency.

NVM $\lambda.proposals$ simplified

Another large amount of overhead can be avoided if leaders keep track of which slots have already been decided. Before turning active, a leader can include in the p1a request the first slot for which it does not know the decision. Acceptors do not need to respond with pvalues for smaller slot numbers. Upon turning active, a leader does not need to start commanders for slots for which it already knows the decision.

RENESSE, P. 12 §4.1 - Paxos Made Pragmatic

For $\lambda.proposals$, we are only concerned about slots that have not reached consensus from acceptors and learned by the replicas. They are not in context, nor do they need commanders. This allows them to be excluded from the p1b messages sent by acceptors. On acknowledgments from replicas, a proposal can be removed from the state since it is no longer needed, keeping the state relatively small.
