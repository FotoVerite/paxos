Reconfiguration

Paxos assumes a fixed set of replicas. But real systems need to add nodes, remove nodes, or replace nodes. This is reconfiguration.

The naive approach—just change the replica set—breaks consensus. The majority quorum might shift, violating safety. You need a protocol for changing configurations safely.

The reconfiguration trick

The solution is elegant: treat reconfiguration as a command. A special command that changes the replica set.

When you want to add a node, you propose a command "Add node 5" through the normal Synod protocol. Once it's decided and executed by a majority, the new node joins the system.

Similarly, "Remove node 3" becomes a decided command. Once executed, quorum calculations don't include that node anymore.

Why this works

By using the consensus protocol itself to coordinate configuration changes, you ensure that all nodes agree on when to switch to the new configuration.

Here's the key: you can have a transition period where the system operates under a "joint consensus" rule. The old replica set and new replica set both need to agree. This ensures safety during the transition. Once everyone moves past the transition, the new quorum takes effect.

Practical considerations

When adding a node, it starts empty. It needs to catch up on all previous decisions. The system can serve this new node's state transfer requests in parallel with normal operation, but the new node isn't counted toward quorum until it's caught up.

When removing a node, you actually want it to be slow or dead. Otherwise, if you remove a node that's still alive and talking to clients, it might confuse them by continuing to respond to requests even though it's no longer part of the cluster.

Van Renesse's paper mentions that full reconfiguration details are beyond the scope and points to other work. The main idea is: use consensus to coordinate, and be careful about quorum rules during transitions.
