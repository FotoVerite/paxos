Optimizations

The core Paxos protocol works, but it can be slow. Every command goes through scouts and commanders, which means lots of messages and disk writes. Real systems need to be much faster.

This section covers techniques that speed up Paxos without breaking correctness.

Batching

Instead of proposing one command at a time, batch multiple commands into a single slot. The leader collects client requests and proposes them as a batch.

This amortizes the cost of scouts and commanders across many commands. One round of consensus can commit 100 commands instead of 1.

The downside: latency increases for individual commands (they have to wait for the batch to fill). The tradeoff is tunable: bigger batches = higher throughput but higher latency.

Pipelining

Once the leader has a stable majority, it can propose multiple slots in parallel. Instead of waiting for slot 1 to be decided before proposing slot 2, the leader sends commanders for slots 1, 2, 3, and beyond all at once.

Acceptors process these in sequence, but the network latency is hidden. By the time the leader hears back about slot 1, acceptors are already processing slots 2 and 3.

This increases throughput significantly on high-latency networks.

Skipping scouts

If the leader is stable and successfully proposing values, it doesn't need to run a new scout for every command. It can reuse the same ballot for many commands.

A scout only needs to happen when the leader changes or when a ballot fails. During normal operation, the same ballot is used for many commands.

Acceptor colocation

Acceptors are often colocated with replicas. Instead of sending messages to separate acceptor processes, the replica just calls the acceptor directly (in-process).

This reduces message count and latency significantly. The tradeoff is that acceptor state must be persisted on the same machine as the replica state.

Leader colocation

Similarly, leaders can be colocated with replicas or acceptors. This reduces round-trip latencies.

The result is that in many real systems, you have just N machines, each running a replica, acceptor, and leader. Messages are mostly inter-machine (slower) rather than intra-machine (fast).

Garbage collection

Over time, the pvalues set (accepted values) grows unboundedly. Acceptors eventually can't store them all.

Van Renesse mentions that you can safely discard pvalues for slots that are far in the past (slots that all replicas have already executed). The details are tricky but important for long-running systems.

Connection pooling and batching at lower layers

At the TCP level, you can batch multiple Paxos messages into a single packet, or maintain persistent connections to avoid TCP handshake overhead.

These are implementation details, but they matter for achieving the high throughput you see in real systems like Google's Chubby.
