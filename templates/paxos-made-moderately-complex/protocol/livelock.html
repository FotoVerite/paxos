Live-Locks

Definition

Consider the following scenario, with two leaders with identifiers $\lambda$ and $\lambda'$ such that $\lambda < \lambda'$. Both start at the same time, respectively proposing commands $c$ and $c'$ for slot number 1. Suppose there are three acceptors, $\alpha_1$, $\alpha_2$, and $\alpha_3$. In ballot (0, $\lambda$), leader $\lambda$ is successful in getting $\alpha_1$ and $\alpha_2$ to adopt the ballot, and $\alpha_1$ to accept pvalue $((0, \lambda), 1, c)$.

Now leader $\lambda'$ gets $\alpha_2$ and $\alpha_3$ to adopt ballot $(0, \lambda')$ (which is after $(0, \lambda$) because $\lambda < \lambda'$). Note that neither $\alpha_2$ nor $\alpha_3$ accepted any pvalues, so leader $\lambda'$ is free to select any proposal. Leader $\lambda'$ then gets $\alpha_3$ to accept $((0, \lambda'), 1, c')$.

At this point, acceptors $\alpha_2$ and $\alpha_3$ are unable to accept $((0, \lambda), 1, c)$, and thus leader $\lambda$ is unable to get a majority of acceptors to accept $((0, \lambda), 1, c)$. Trying again, leader $\lambda$ gets $\alpha_1$ and $\alpha_2$ to adopt $(1, \lambda$). The maximum pvalue accepted by $\alpha_1$ and $\alpha_2$ is $((0, \lambda), 1, c)$, and thus $\lambda$ must propose $c$. Suppose $\lambda$ gets $\alpha_1$ to accept $((1, \lambda), 1, c)$.

Because acceptors $\alpha_1$ and $\alpha_2$ adopted $(1, \lambda)$, they are unable to accept $((0, \lambda'), 1, c')$. Trying to make progress, leader $\lambda'$ gets $\alpha_2$ and $\alpha_3$ to adopt $(1, \lambda')$, and gets $\alpha_3$ to accept $((1, \lambda'), 1, c')$.

RENESSE, P. 9 §3 - When Paxos Works

What Renesse is describing here is a live-lock. The system is still sending messages, but those messages short circuit the protocol out leading to no actual progress in any proposal being decided on. And even if a command is decided on, the constant switching of leadership leads extreme message cascades that can drive the entire system to a standstill. This type of live-locking does not pertain to PAXOS but to any deterministic consensus protocol with failures in an asynchronous environment.

FLP

This ping-pong scenario can be continued indefinitely, with no ballot ever succeeding in choosing a pvalue. This is true even if c = c', that is, the leaders propose the same command. The wellknown “FLP impossibility result” demonstrates that in an asynchronous environment that admits crash failures, no consensus protocol can guarantee termination, and the Synod protocol is no exception.

RENESSE, P. 10 §3 - When Paxos Works

The 📄 FLP impossibility result ↗ states that in a fully asynchronous distributed system, no deterministic algorithm can guarantee consensus if even one process may crash. This is because messages can be delayed arbitrarily, making it impossible for processes to distinguish a slow process from a crashed one, so the system can be forced into indefinite indecision. Liveness and Safety work via different means.Safety can always be preserved by delaying decisions. Liveness requires eventually committing to a decision, and in a fully asynchronous system this cannot be guaranteed without risking safety.

Randomized States

The argument does not apply directly if transitions have non-deterministic actions—for example changing state in a randomized manner. However, it can be demonstrated that such protocols cannot guarantee a decision either.

RENESSE, P. 10 §3 - When Paxos Works

One can say, well I can just add delays to the messages to cut down on chatter. This will work for increasing liveness, but still allows for potential live-locks. A long running system will run into these potentials even if they are a 1 in a billion likely-hood.
