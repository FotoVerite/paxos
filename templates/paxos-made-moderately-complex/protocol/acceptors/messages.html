Acceptor Messages

Execution Model
It [An acceptor] runs in an infinite loop, receiving two kinds of request messages from leaders
RENESSE, P. 5 §2

Phase 1a

Phase 1
(p1a, λ, b): Upon receiving a “phase 1a” request message from a leader with identifier λ, for a ballot number b, an acceptor makes the following transition. First, the acceptor adopts b if and only if it exceeds its current ballot number. Then it returns to λ a “phase 1b” response message containing its current ballot number and all pvalues accepted thus far by the acceptor.
RENESSE, P. 5 §2

Phase 1a message is similar to the propose message from Lamport's Part Time Parliament paper. Instead of being concerned with the current ballot history it is concerned with the accepted history of the acceptor.

λ is the leader ID, which can be assumed to be an orderable integer

Here the Leader is querying the acceptor on it's history. This will allow it to determine precedence of values for a given slot and to propose commands accordingly

It also initiates a state change for the ballot. If the ballot is greater then the current ballot for the acceptor it will adopt it as it's α.ballot_num. If it's equal or less no state change happens.

After the potential state change the acceptors sends back all accepted pvalues in it's α.accepted. This mirrors the “promise” message from Part-Time Parliament: no value is proposed yet, but by adopting ballot b, the acceptor ensures it won’t accept any Phase 2A messages with a lower ballot. Ballots are global, so the response covers all slots rather than a single one.

Phase 2a

Phase 2
(p2a, λ,(b, s, c)): Upon receiving a “phase 2a” request message from leader λ with pvalue (b, s, c), an acceptor makes the following transition. If b exceeds the current ballot number, then the acceptor first adopts b. If the current ballot number equals b, then the acceptor accepts (b, s, c). The acceptor returns to λ a “phase 2b” response message containing its current ballot number
RENESSE, P. 5 §2

Phase 2a messages are almost identical to the accept message from Lamport's Part-Time Parliament paper. The leader requests that the acceptor accept the proposed pvalue.

The acceptor updates its α.ballot_num to be at least the ballot b in the message. It then accepts the pvalue only if α.ballot_num equals b.

The acceptor responds with a Phase 2b message containing its current α.ballot_num. This response does not explicitly indicate acceptance; the leader must infer acceptance by comparing the returned ballot number with the one it sent. If they match, the acceptor accepted the pvalue.

Invariant Enforcement
It is easy to see that the code enforces Invariants A1, A2, and A3. For checking the remaining two invariants, which involve multiple acceptors, we have to study what a leader does first.
RENESSE, P. 5 §2

A1: Ballot Ordering and A2: Ballot Consistency are enforced because the acceptor ignores Phase 2a messages with ballots lower than its current α.ballot_num.

A3: Append Only is enforced because the acceptor never removes entries from α.accepted.
