Reconfiguration Made Easy

Definition

A configuration is the set of processes (clients, acceptors, learners, etc.) that are executing the system. The consensus algorithm used to implement a state machine assumes a fixed configuration, so each instance of that algorithm must execute under a single configuration. (It is the set of acceptors that is important; adding or removing clients or learners while executing a consensus algorithm is not a problem.)

LAMPORT, P. 3 §2.3- Reconfiguration Made Easy

It is useful to start with a precise definition of configuration. In Paxos, consensus for a particular command is executed by a fixed set of acceptors.That set cannot change once a slot is being decided.

This does not mean the system can never change. Instead, each command in the log is associated with a configuration. A decision made using one configuration remains tied to that configuration even if later commands use a different one.

For example, suppose command $i$ is decided using five acceptors. The quorum requirements for that decision remain based on those five nodes. Removing two of them later does not retroactively shrink the quorum, and adding new nodes does not increase it.

This is why adding learners, clients, or proposers is usually easy. They do not affect the quorum system that guarantees safety. Changing acceptors is harder because it alters the structure the algorithm relies on.

Protocol $\mathcal{R_1}$

In the easy approach, reconfiguration is achieved by using different configurations for different instances. We define the configuration at command number $i$ to be the one used to execute consensus instance $i$.

To prevent chaos, processes must agree on the configuration at command $i$. The easy way to obtain a reconfigurable state-machine implementation is to introduce a component $cfg$ of the state-machine state that specifies the current configuration.

In other words, the configuration at command $i$ is determined by the value of $cfg$ in the state immediately following execution of command $i - 1$, or by its initial value if $i = 1$. (We use ordinal numbers for commands, so the first command is number $1$.)

We add reconfiguration commands of the form $rcfg(C)$, which specifies a new configuration $C$.

The obvious way to define the state machine is to let executing $rcfg(C)$ set $cfg$ to $C$, so reconfiguration occurs immediately. We call this method $\mathcal{R_1}$. The problem with $\mathcal{R_1}$ is that it prevents concurrent processing of different proposed commands. Since the configuration used to execute instance $i + 1$ of the consensus algorithm can be changed by executing command $i$, the state-machine implementation cannot begin choosing command $i + 1$ until command $i$ has been chosen

LAMPORT, P. 3 §2.3- Reconfiguration Made Easy

Lamport's easy solution is to define a configuration for each slot, beginning with the first slot. $rcfg(C)$ is a command itself, so every configuration change must pass through the system in order to take effect. Because of this, the configuration for slot $i$ is determined by the state produced by slot $i - 1$. The system must first reach consensus on that state before the next slot knows which configuration to use.

If the configuration were allowed to change immediately (Lamport calls this approach R1), the system could not safely process multiple slots at the same time. Without this invariant, a slot would have no reliable way to know whether it was using the correct configuration.

The consequence is that proposals effectively serialize: slot $i$ must be decided before slot $i + 1$ can safely begin. That obviously hurts performance.
