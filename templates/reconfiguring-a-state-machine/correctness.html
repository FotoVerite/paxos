Correctness

$\mathcal{B2}$   Invariant and Liveness

A simple induction argument shows that $\mathcal{R_\alpha}$ maintains the safety property of a state-machine implementation. In particular, it satisfies irrevocability.

Liveness for a state-machine implementation states that it makes progress if enough servers are nonfaulty. Reconfiguration raises the question, enough of which servers? The purpose of reconfiguration is to eliminate the dependence on servers that have been reconfigured out of the system. Information maintained by those servers must be transferred to servers in the new configuration.

This is done by garbage collecting consensus instances executed under the old configuration and transferring the state to the new configuration’s learners. During the transition to the new configuration, progress is guaranteed only if there are enough nonfaulty servers from both the old configuration and the new one. The liveness property satisfied by the resulting algorithm is not easy to state precisely, but its general nature should be intuitively clear.

LAMPORT, P. 4 §2.4- Correctness

Lamport argues that the protocol preserves irrevocability. Irrevocability corresponds to the $\mathcal{B2}$ invariant: once a command has been chosen for a slot, no different command can ever be chosen for that slot. The reconfiguration command itself is just another state-machine command, so the same guarantee must hold for it as well.

Liveness is harder to reason about. During reconfiguration the system may temporarily depend on servers from both the old configuration and the new one. If too many servers from the old configuration fail before the new configuration is fully established, the system may be unable to make progress.

Lamport does not discuss $\mathcal{B1}$ or $\mathcal{B3}$ explicitly. The reconfiguration mechanism does not change how commands are proposed or chosen, so the underlying Paxos guarantees remain intact. As a result, validity and consistent execution continue to hold.
