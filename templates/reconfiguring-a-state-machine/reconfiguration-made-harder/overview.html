Reconfiguration Made Harder

The Problem

Algorithm $\mathcal{R_\alpha}$ of Section 2.3 has the practical drawback that a reconfiguration introduces a sequence of noop commands of length about $\alpha$. This can be inconvenient for large values of $\alpha$ —for example, $\alpha$ = $2^{64}$. The bound on concurrency implied by $\alpha$, even if not a practical concern, may also be considered inelegant. We now present reconfiguration algorithms that permit any number of commands to be chosen concurrently during normal execution, when no reconfiguration is in progress.

LAMPORT, P.4 $ §3

While the previous protocol works, Lamport dislikes it because he feels it's hacky and inelegant. The approach spreads configuration logic throughout the log and introduces an artificial bound on concurrency determined by $\alpha$. He also points out that the fast-foreword trick of the no-ops he can cause slowdown at large a $\alpha$ and also pollutes the log further. Instead he has come up with a more complicated method that will work with the system concurrently and with less log pollution. The system will executes a sequence of ordinary non-reconfigurable state machines.

He wants to shift configuration from log positions to the lifetime of a particular state-machine instance.

The Solution

We obtain a reconfigurable state-machine implementation by combining the executions of a sequence of separate non-reconfigurable state-machine implementations. To reconfigure when executing state-machine implementation number $v$, we stop that execution, choose the new configuration, and start the execution of statemachine implementation number $v + 1$ by that configuration. The starting state of state machine $v + 1$ is the final state of state machine $v$.

This approach requires solving three largely orthogonal problems: (i) stopping the current state machine, (ii) choosing the configuration to implement the next state machine, and (iii) combining the sequence of commands chosen for each separate state machine into a single sequence. We consider them separately, starting with three basic methods for implementing a stoppable state machine.

LAMPORT, P.5 $ §3

Each new state machine begins from the final state of the previous one. In modern systems that state is always a snapshot of the the replica after stop has been called.

If the system is currently running state machine $v$, reconfiguration is performed by stopping it, selecting a new configuration, and starting state machine $v + 1$ with that configuration and the state $v$'s snapshot.

In this sense, the sequence of state machines forms a single logical history. State machine $v+1$ continues execution from the state/snapshot produced by $v$, and later machines continue from the ones before them.

This approach requires solving three largely independent problems.

  • Stopping the current state machine
  • Choosing the configuration for the next state machine
  • Combining the commands chosen by each machine into a single history
