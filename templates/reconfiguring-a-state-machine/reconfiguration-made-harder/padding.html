Padding

Padding

We have already observed that we can batch a sequence of commands and process them essentially as easily as a single command. This applies equally well to an infinite sequence of consecutive commands, if all but a finite number of them are noop commands. (It is easy to devise a finite encoding of the information needed to execute the infinite number of consensus instances.) In the Padding method, a client stops the state machine by proposing an infinite number of noop commands. More precisely, it proposes noops for all commands numbered greater than some i. When command number j has been chosen for all positive integers j, the state machine has stopped.

LAMPORT, P.5 $ §3.1.2 - Padding

I’m going to be blunt: “infinite noops” is a mathematical move, not something you literally run. This is Lamport going off on his math journey and how to define consensus in TLA+. Padding is a instruction that configures the leaders. It's a fucking boolean or state change that forces a leader to propose only no-ops after a slot number $j$

Commands may still be chosen after the logical end of the computation, but they have no effect on the state. While this is mathematically clean and preserves safety, it is operationally awkward and makes the log harder to reason about, since the system never produces a clear “last command.”. Padding is simply a reconfiguration of the leader, there is no history in the log itself to indicate it was called. During the transition between state machines $v$ and $v+1$, the log may contain commands that are chosen but end up doing nothing.
